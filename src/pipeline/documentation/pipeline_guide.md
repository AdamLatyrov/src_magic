# Как проходит анализ

Pipeline анализирует упорядоченные кадры пути по критериальному каталогу. Он собирает кандидаты, сводит их, сопоставляет с переданными прошлыми находками и возвращает итог. Здесь описано текущее поведение, без предположений о будущих этапах.

## Ответственность интеграции

Интеграция выбирает продукт и редакцию каталога, получает кадры и прошлые находки, приводит решение эксперта к `pending`, `approved` или `rejected`, создаёт свою задачу и сохраняет состояние и итог. Она передаёт готовые `GraphSettings`, `CXCriteriaModel` и провайдер в фасад.

Pipeline не подключается к базе, очереди или S3. Его состояние не переживает перезапуск процесса. Интеграция сохраняет полученные снимки у себя.

## Этапы одного прогона

1. `start(request)` проверяет run ID и начинает задачу. Текущий статус доступен через `get_state_json`.
2. `scan_journey_frame` последовательно разбирает изображения и фиксирует наблюдения по каждому экрану.
3. `summarize_journey` собирает описание маршрута и определяет, похож ли набор кадров на пользовательский путь.
4. Если путь подтверждён, параллельно запускаются `criteria_model_frames`, `screen`, `journey_frictions` и `autofill`. Каждая ветка выполняет свои проверки.
5. `consolidate_findings` сводит результаты активных веток в общий перечень.
6. При наличии истории `dedup_findings` сопоставляет прошлые и текущие находки с учётом решения эксперта.
7. Оценка пересчитывается по итоговому списку. Результат возвращается завершившейся задаче.

Если последовательность не подтверждена как пользовательский путь, ветки поиска проблем пропускаются. Этот случай нужно отличать от завершённого анализа без находок.

## Что означают снимки

`get_state_json(run_id)` возвращает накопленную картину на момент вызова. В начале список этапов может быть пуст. Позже появляются запущенные и завершённые этапы, счётчики, общая и аналитическая оценка статуса, причины деградации, сбойные блоки и fallback-ответы.

`revision` растёт при каждом обновлении. Интеграция может сохранять снимок, только если его ревизия новее сохранённой. `updated_at` показывает, когда фасад обновил снимок. После завершения задача возвращает полный `PipelineRunResult`.

Прогресс API не является трассировкой запросов модели. Он не возвращает промпты, ответы модели или сами изображения. Так проще безопасно передавать статус через HTTP, не раскрывая содержание анализа.

## Лимит выполнения графа

Фасад рассчитывает `recursion_limit` по числу кадров формулой `max(50, frames * 4 + 50)`. Это верхняя граница внутренних циклов LangGraph, а не лимит кадров или обращений к модели. Например, для 30 кадров предел равен 170. Формула задана в коде и не читается из environment.

## Демонстрационный запуск

`main_notebook.ipynb` загружает конфигурацию и пример каталога из `pipeline/demo_assets`, создаёт провайдера GigaChat из окружения, передаёт три изображения в фасад, показывает меняющиеся снимки и выводит итоговые находки. Данные демонстрационные. Они не являются GoldSet, а полный запуск обращается к настроенной модели и может занять несколько минут.
