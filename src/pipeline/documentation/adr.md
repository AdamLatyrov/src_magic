# Решения по устройству pipeline

Здесь записаны решения, которые влияют на границу между анализом и интеграцией. Каждая запись объясняет выбранный вариант и его цену.

## ADR-001. Вызов через один фасад

Статус - принято

Контекст - интеграции нужен единый вход в анализ скриншотов. Если она напрямую вызывает узлы графа, ей придётся знать внутреннее устройство LangGraph и порядок его веток.

Решение - создавать `AnalysisPipeline` из настроек графа, критериальной модели и провайдера, затем передавать один `PipelineRequest` в `start`.

Почему - фасад проверяет зависимости и держит стабильную точку вызова, пока внутренний граф меняется.

Последствия - интеграция всё ещё отвечает за выбор продукта, версии каталога, модели и провайдера. Наличие пяти методов у провайдера не доказывает, что удалённая модель совместима.

## ADR-002. Прогресс живёт в памяти процесса

Статус - принято для текущего этапа

Контекст - pipeline нужен интеграции, которая уже управляет задачей и её хранением. Собственная очередь или база в pipeline продублировала бы эту ответственность.

Решение - `start` возвращает `asyncio.Task`. `get_state_json(run_id)` отдаёт последний накопленный снимок. Полный результат возвращает завершившаяся задача.

Почему - интеграция может получить готовый JSON-снимок для своего HTTP-ответа, не читая внутреннее состояние графа.

Последствия - снимки и задача существуют только в памяти текущего процесса. После его перезапуска продолжить прогон или прочитать старое состояние нельзя. Интеграция сохраняет снимки и результат у себя. Отдельного метода `get_result` нет.

## ADR-003. Снимок прогресса отделён от итогового ответа

Статус - принято

Контекст - во время анализа ещё нет полного результата, но интеграции нужны статус, текущий этап и накопленная диагностика.

Решение - `PipelineProgressSnapshot` хранит статус прогона, этапы, ревизию, время обновления, статус анализа, деградацию, сбойные блоки и использованные обходные ответы. `PipelineRunResult.state` сохраняет прежний тип `PipelineStateSnapshot`.

Почему - прогресс можно читать по `run_id`, не меняя форму финального результата.

Последствия - снимок не содержит сырые запросы к модели, тексты ответов или изображения. Эти данные могут включать клиентскую информацию и не нужны HTTP-каналу прогресса.

## ADR-004. Вход содержит историю и решение эксперта

Статус - принято

Контекст - повторный прогон должен учитывать прежние находки и решение эксперта, иначе нельзя понять, что сохранилось, исчезло или появилось заново.

Решение - интеграция передаёт `previous` со статусом `pending`, `approved` или `rejected`. Pipeline сравнивает их с текущими находками и пересчитывает оценку по итоговому списку.

Почему - единые статусы устраняют неоднозначность при передаче данных между системой интеграции и анализом.

Последствия - для отклонённых находок точное совпадение определяется по стабильному адресу дефекта. Семантический дубль с другим адресом автоматически не гарантирован.

## ADR-005. Настройки графа, каталог и провайдер передаются готовыми

Статус - принято

Контекст - pipeline не должен выбирать продукт, читать настройки процесса интеграции или открывать соединения с хранилищами.

Решение - вызывающая сторона заранее собирает `GraphSettings`, `CXCriteriaModel` и объект, совместимый с `PipelineProvider`.

Почему - внутренний пакет остаётся библиотекой анализа и не зависит от БД, очереди и объектного хранилища.

Последствия - для каждого продукта интеграция выбирает соответствующий каталог и конфигурацию. `product_name` и `product_type` записываются в результат, но не подмешиваются в запрос модели.

## ADR-006. Документация поставляется вместе с кодом

Статус - принято

Контекст - комплект передаётся как папка `src`; документация вне неё теряется при копировании.

Решение - контракт, руководство, ADR, обзор кода и результаты проверок хранятся в `pipeline/documentation`. Главный README и ноутбук лежат рядом с `main.py`.

Почему - интегратору достаточно открыть переданный комплект, чтобы увидеть интерфейс, пример и ограничения.

Последствия - при изменении публичных схем нужно синхронно сверить `main.py`, README, контракт и ноутбук.
