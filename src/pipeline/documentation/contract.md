# Контракт интеграции с pipeline

Публичные схемы находятся в `pipeline/schemas/api.py`, фасад - в `main.py`. Pipeline получает уже подготовленные данные и не ищет продукт, не читает БД, очередь или S3.

## Что подготовить один раз

Создайте три объекта и передайте их в `AnalysisPipeline`.

1. `GraphSettings` задаёт этапы графа, промпты, модели и параметры генерации.
2. `CXCriteriaModel` содержит критериальный каталог нужной версии.
3. `provider` реализует методы `PipelineProvider`, перечисленные ниже.

Интеграция выбирает соответствующие продукту настройки и каталог. Она же создаёт провайдера и отвечает за его ключи и сертификаты. Pipeline не импортирует `integration`.

## Что передать на каждый прогон

Создайте `PipelineRequest` со следующими полями.

| Поле | Назначение |
| --- | --- |
| `run_id` | Необязательный идентификатор. Если его не задать, создаётся UUID. |
| `product_name` | Название продукта для атрибуции результата. |
| `product_type` | Тип продукта в словаре интеграции. Pipeline не проверяет этот словарь. |
| `frames` | Один или несколько `CXFrame` в порядке шагов. У каждого кадра положительный возрастающий `step` и изображение в `data_url`. |
| `screenshot_keys` | Необязательные ссылки интеграции на кадры в том же порядке. Если список передан, его длина должна совпадать с числом кадров. |
| `previous` | Прошлые находки этого продукта в виде `PreviousFinding` с решением `pending`, `approved` или `rejected`. По умолчанию список пуст. |
| `material` | Необязательная заметка эксперта. Этот текст может попасть в запрос модели. |

`product_id` в `PipelineRequest` не нужен. Pipeline сохраняет название и тип продукта в ответе, но не использует их как подсказку модели. До вызова интеграция проверяет, что история и каталог относятся к тому же продукту и совместимой редакции критериев.

Для `pending` эксперт ещё не подтвердил находку. При совпадении используется актуальная формулировка. Для `approved` сохраняется текст прошлой находки, а доказательства и шаги обновляются результатом текущего прогона. Для `rejected` прошлое исключается из сверки. Новая находка снимается только при совпадении точного адреса дефекта; семантический дубль с другим адресом автоматически не гарантирован.

## Запуск

`start` нужно вызывать внутри работающего цикла asyncio. Он сразу возвращает `asyncio.Task`.

```python
pipeline = AnalysisPipeline(settings, catalog, provider)
request = PipelineRequest(
    product_name=product_name,
    product_type=product_type,
    frames=frames,
    screenshot_keys=screenshot_keys,
    previous=previous_findings,
    material=expert_comment,
)

task = pipeline.start(request)
```

## Чтение текущего состояния

Когда клиент запрашивает прогресс, HTTP-обработчик интеграции получает готовый JSON-совместимый словарь:

```python
snapshot = pipeline.get_state_json(request.run_id)
return snapshot
```

Снимок накапливает этапы и поля состояния на момент чтения. В него входят `run_id`, общий статус, этапы с их длительностью и счётчиками, ревизия, время обновления, статус анализа, признак деградации, причины, ошибки блоков и использованные fallback-ответы. В состоянии `queued` часть этих полей ещё пуста.

HTTP-обработчик может вызвать метод при каждом запросе клиента. Сам pipeline не создаёт HTTP-сервер и не опрашивает себя в фоне. Интеграции не нужно писать callback для обычного чтения состояния.

`get_state(run_id)` возвращает типизированную модель того же снимка. `on_event` остаётся необязательным параметром `start` ради совместимости. Callback синхронный и получает базовый `PipelineStateSnapshot`; его не следует использовать вместо расширенного `get_state_json`.

Снимки хранятся в памяти экземпляра `AnalysisPipeline` в одном процессе. После перезапуска они пропадают. Интеграция должна сохранять каждую новую ревизию в своём хранилище. Снимок прогресса намеренно не содержит кадры и необработанный обмен с моделью.

## Получение итогового результата

Завершившаяся задача возвращает `PipelineRunResult`:

```python
result = await task
```

Отдельного метода `get_result` нет. Итог содержит `run_id`, продуктовую атрибуцию, полный объект `analysis`, итоговый список `findings` и финальное состояние `state`. `findings` и `analysis.issues` - список проблем после сверки истории. `analysis.pipeline` может содержать промежуточные исходные находки для диагностики.

Интеграция сохраняет итог и завершает свою задачу. Если из `await task` выходит исключение, оно передаётся вызывающему коду. Долговременного результата по `run_id` внутри pipeline нет.

Не считайте пустой список проблем доказательством чистого пути без проверки общего статуса, статуса анализа, этапов и `is_degraded`.

## Методы провайдера

Фасад убеждается, что у провайдера есть пять вызываемых методов. Типы, форматы и доступность сети подтверждаются только отдельным прогоном.

- `chat(request_options, tools=None, tool_choice=None)` возвращает `ChatResponse`.
- `chat_structured_output(request_options, structured_output, method="format_instructions")` возвращает объект заданной Pydantic-модели.
- `chat_with_structure_output_with_frames(request_options, structured_output, method="format_instructions")` возвращает объект заданной модели для запроса с изображениями.
- `upload_frame(options, model, data_url)` загружает изображение и возвращает ссылку провайдера.
- `delete_frames(options, model, file_ids)` удаляет временные ссылки.

Формы `ChatRequest`, `ChatResponse` и `ChatOptions` определены в `pipeline/aef/models.py`. Конкретный адаптер GigaChat находится в `pipeline/aef/patterns/gigachat_provider.py`.

## Что сейчас не поддерживается

- сохранение состояния самим pipeline;
- чтение состояния после перезапуска процесса;
- продолжение упавшего прогона с выбранного этапа;
- поиск готового результата по `run_id` без сохранённого объекта задачи;
- получение сырых запросов и ответов модели через прогресс API.
